## 今日重点讨论补充

### json-repair 的正确工程位置

推荐链路：

```text
LLM raw output
-> extract JSON candidate
-> json-repair
-> json.loads
-> Pydantic / JSON Schema validation
-> risk classification
-> permission gate
-> sandbox / dry-run
-> execution trace
```

关键边界：

```text
json-repair 解决：文本是不是可解析 JSON
schema validation 解决：字段和类型是否符合结构
permission gate 解决：动作是否允许执行
trace 解决：事后能否审计和复盘
```

### 和约束解码的区别

| 维度 | json-repair | 约束解码 / JSON mode / Structured Outputs |
|---|---|---|
| 发生时机 | 模型输出之后 | 模型生成 token 过程中 |
| 核心机制 | 容错解析 + 启发式补全 | 限制可生成 token 或 schema |
| 主要目标 | 修复坏 JSON | 从源头生成合法结构 |
| 可靠性 | 可能修错或误补 | 语法/结构稳定性更强 |
| 适合场景 | 兜底、历史坏数据、多 provider 兼容 | 工具调用、高风险动作、生产 API |
| 安全边界 | 不提供权限保护 | 仍需业务权限和 guardrails |

## 新概念/新框架/新协议/新评测

- **JSON Repair Trace**：记录模型原始输出、修复结果、schema 校验结果、下游动作和权限决策；重要性在于结构化输出失败也应进入 Agent Observability。
- **Post-processing Repair**：模型输出后的格式修复层；重要性在于它适合兜底，但不能约束模型生成过程。
- **Constrained Decoding / Structured Outputs**：生成阶段限制 token 或 schema；重要性在于它比后处理更适合工具调用参数和生产结构化输出。
- **Repair Is Not Permission**：修好 JSON 不代表允许执行；重要性在于 Agentic Coding 和 tool calling 的安全边界必须独立实现。
- **Schema Validation after Repair**：修复后继续用 Pydantic / JSON Schema 校验；重要性在于防止“合法 JSON 但字段错误或业务不合法”。
- **Source Trace for Daily Report**：日报生成要记录早间雷达是否存在、缓存是否过期、是否降级；重要性在于防止 Agent 报告链路虚构来源。
